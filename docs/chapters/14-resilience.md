# 14장. 모델 서버가 실패하면 답도 실패한다: 장애 대응

## 문제

13장까지 모델 호출은 한 번 보내고 실패하면 끝이었다. 오픈라우터 호출이 429(속도 제한)나 5xx를 내면 예외가 나서 `proviso agent ask`는 답을 못 하고, 평가 실행은 통째로 멈췄다. 9장에서 API 모델로 test 171문항을 돌릴 때도 한 번의 오류가 실행 전체를 버리게 할 수 있었다. 계획서 §5.5의 장애 대응을 이 장에서 넣는다.

## 처방

모두 `agent/resilience.py`와 `agent/loop.py`의 호출부에 있다.

| 처방 | 내용 |
|---|---|
| 시간 한도 | API 호출 하나에 60초. 로컬 모델은 긴 자료에서 수십 초씩 걸려 600초로 둔다 |
| 재시도 | 429·5xx·연결 오류·시간 초과만 최대 3번. 1·2·4초(최대 30초)에 0~25% 흔들림. 서버가 `Retry-After`를 주면 그만큼 기다린다. 400·401·404는 다시 보내도 같아서 재시도하지 않는다 |
| 속도 제한 | 회사(API 주소)마다 분당 60회를 넘지 않게 기다린다. 같은 회사 모델끼리 한도를 나눠 쓴다 |
| 대체 모델 | `ask`는 DeepSeek V4 Flash → GLM-5.3 Flash(다른 회사) → 로컬 qwen3.5 4b 순으로 써 본다. 순서는 9장(거절 정확도)과 13장(충실도) 결과다. 대체가 답하면 기록에 `fallback_from`을 남긴다 |
| 차단기 | 같은 모델이 연속 2번 실패하면 60초 동안 그 모델을 건너뛴다. 장애 중에 매번 재시도 시간을 쓰지 않으려고 |
| 평가 실행 | 대체를 쓰지 않는다. 다른 모델의 답이 섞이면 비교가 깨지므로, 실패한 문항은 `error`로 남기고 채점에서 뺀다(거절로 세지 않는다). 실행은 멈추지 않는다 |
| 모두 실패 | `ask`는 "지금은 답변 모델에 연결하지 못해 답할 수 없습니다. 잠시 뒤 다시 물어 주세요."라고 답한다 |

오류 글에는 공급자 응답 본문 대신 `error.message`만 남긴다. 처음에는 본문 앞 300자를 남겼는데, 오픈라우터 오류 본문에 계정 id(`user_id`)가 들어 있어 기록에 남았다. 고친 뒤 그 기록에서도 지웠다. API 키는 전처럼 어떤 기록에도 남기지 않는다(테스트로 확인).

## 장애 주입 테스트

`tests/test_resilience.py`가 모의 서버(`httpx.MockTransport`)로 장애를 일으킨다. 실제 API는 부르지 않는다.

- 429(Retry-After 7초) → 500 → 성공: 3번째에 답하고, 7초와 약 2초를 기다린다.
- 503만 낸다: 4번(첫 시도 + 재시도 3번) 보내고 실패한다.
- 시간 초과는 다시 보내고, 400은 한 번만 보낸다.
- 1순위가 계속 500: 대체 모델이 답하고 `fallback_from`이 붙는다. 2번 실패한 뒤 세 번째 질문에서는 1순위를 건너뛰고, 60초가 지나면 다시 써 본다.
- 오류 글에 키와 계정 id가 없다. 실패한 평가 문항은 채점 값이 없다.

## 장애 주입 실험

모의 서버와 가상 시계로 장애 다섯 가지를 일으켜, 같은 100문항을 세 가지 방식으로 보냈다(`python -m proviso.agent.chaos`, seed 0, 비용 0원). 질문 하나는 모델 호출 3번이고 하나라도 실패하면 질문이 실패다. 질문은 12초마다 들어온다. 응답 시간은 1순위 3초, 대체 4초 안팎이다.

| 장애 | 대응 없음 | 재시도 | 재시도 + 대체 |
|---|---:|---:|---:|
| 정상(5xx 1%) | 0.95 | **1.00** | **1.00** |
| 속도 제한(429 30%) | 0.37 | 0.99 | **1.00** |
| 서버 오류(5xx 20%) | 0.50 | 0.99 | **1.00** |
| 느린 응답(10%가 90초) | 0.65 | **1.00** | **1.00** |
| 1순위 장애(200~600초 동안 모두 503) | 0.63 | 0.67 | **1.00** |

(질문 성공률)

| 성공한 질문의 지연 p50 / p95 | 대응 없음 | 재시도 | 재시도 + 대체 |
|---|---|---|---|
| 정상 | 9.1 / 10.6초 | 9.0 / 10.9초 | 9.0 / 10.9초 |
| 속도 제한 | 9.1 / 10.6초 | 10.8 / 17.6초 | 11.1 / 17.8초 |
| 서버 오류 | 9.1 / 10.6초 | 9.8 / 15.2초 | 9.9 / 15.2초 |
| 느린 응답 | 9.3 / 10.6초 | 9.9 / **132.0초** | 9.9 / **132.0초** |
| 1순위 장애 | 9.1 / 10.6초 | 9.2 / 10.8초 | 9.5 / 20.7초 |

- **잠깐 생기는 오류(429·5xx)는 재시도로 거의 다 막힌다.** 5xx 1%만 있어도 호출 3번짜리 질문은 5%가 실패했다. 재시도하면 0~1%다. 대가는 p95 지연이 5~7초 늘어나는 것이다.
- **긴 장애는 재시도로 못 막는다.** 1순위가 400초 동안 내려가 있으면 재시도해도 0.67이다. 대체 모델을 두면 1.00이고, 그동안 92번의 호출을 대체 모델이 받았다. 차단기 덕분에 장애 중 1순위로 보낸 요청은 재시도만 쓸 때보다 적었다(334 → 239).
- **느린 응답은 남은 문제다.** 시간 한도 60초를 다 기다린 뒤 다시 보내므로, 성공은 하지만 p95가 132초다. 대체도 돕지 못했다(재시도에서 1순위가 결국 답하므로 대체로 넘어가지 않는다). 시간 한도를 줄이거나, 느릴 때 대체 모델에도 함께 보내는 방법(hedging)이 다음 후보다. 재지 않았다.

이 숫자는 장애 확률을 내가 정한 모의 실험이다. 실제 오픈라우터의 오류율이 아니다.

## 실제로 확인한 것

`proviso agent ask`에 없는 모델 id(`openrouter:deepseek/no-such-model`)를 1순위로 줬다. 오픈라우터가 400("not a valid model ID")을 냈고, 재시도 없이 GLM-5.3 Flash가 답했다. 기록에는 `"model": "z-ai/glm-5.3-flash", "fallback_from": "deepseek/no-such-model"`과 실패 사건이 남았다. 비용은 약 0.002달러였다.

## 한계

- 실제 429·5xx는 일으키지 못했다. 재시도 동작은 모의 서버로만 확인했다.
- 대체 모델의 답은 1순위와 품질이 다르다(9·13장: GLM은 거절 정확도·충실도가 DeepSeek와 비슷하고, 4b는 낮다). 사용자에게 어느 모델이 답했는지는 아직 보여 주지 않고 기록에만 남긴다.
- 속도 제한 값(분당 60회)은 오픈라우터의 실제 한도가 아니라 이 프로젝트의 평가 속도에 맞춘 값이다.
- 회사별 동시 호출 수 제한은 넣지 않았다. 지금 평가는 한 번에 하나씩 부른다.
- 같은 질문의 응답을 저장해 다시 쓰므로(9장), 저장된 응답은 장애와 상관없이 그대로 나온다.

## 다시 돌리기

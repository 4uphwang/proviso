# 16장. 질문마다 모델을 새로 불러온다: 서버

## 문제

15장에서 Phoenix로 기록을 보니 `proviso agent ask` 한 번이 약 90초였고, 그중 70~84초가 첫 검색이었다. 평가 실행에서 같은 검색은 문항당 6초대다. `ask`는 질문마다 새 프로세스라서 BM25 색인, 임베딩 모델(bge-m3), 재정렬 모델(bge-reranker-v2-m3)과 법령을 매번 새로 불러온다는 것이 짐작이었다. 계획서 선택 7번(FastAPI 서버)으로 고친다.

## 처방

- **`Asker`**(`agent/ask.py`): 법령, 법령 이름, 검색기, 기준일별 법령, 조문 개정 이력을 한 번만 불러 두고 `answer(질문)`만 질문마다 부른다. 가리기 → 판별 → 에이전트 → 유출 검사 → 기록 순서는 전과 같다. CLI `proviso agent ask`도 이것을 쓴다(질문 하나에 하나를 만들고 버린다).
- **`proviso serve`**(`serve.py`, FastAPI + uvicorn): 시작할 때 `Asker`를 만들고 검색을 한 번 돌려 모델을 메모리에 올린다(warm-up).

| 엔드포인트 | 하는 일 |
|---|---|
| `POST /ask` | `{"question", "model"}` → 답, 인용, trace_id, 실제로 답한 모델, `fallback_from`, 걸린 초 |
| `GET /ask/stream?q=` | 진행 상황을 SSE로 보낸다. 검색 → 조문 열기 → 모델 → 답(단계 단위, 토큰 단위 아님) |
| `GET /health` | DB 연결, warm-up에 걸린 초, 처리한 질문 수 |
| `GET /trace/{id}` | 기록 하나(JSON) |

- 검색 모델이 맥 GPU(MPS)를 쓰고 DB 연결이 하나라서 질문은 한 번에 하나씩 처리한다(잠금). 로컬 데모용이다.
- 서버의 검색 결과는 파일에 저장하지 않고 프로세스 안에서만 기억한다. CLI는 전처럼 `data/cache/ask_search.json`에 저장한다.
- `PROVISO_OTLP_ENDPOINT`를 주면 답할 때마다 기록을 OTel로 보낸다(15장).

## 결과

### warm-up이 짐작을 확인했다

서버를 띄울 때 검색 모델을 올리는 데 **63.4초**가 걸렸다(`/health`의 `warm_seconds`). 15장에서 첫 검색 시간에서 어림한 준비 시간(65~75초)과 맞는다.

### 같은 10문항: CLI와 서버

에이전트 세트 dev에서 답할 수 있는 현행 문항 10개(seed 0)를 서버(`POST /ask`)에 먼저 보내고, 같은 문항을 CLI(`proviso agent ask`, 매번 새 프로세스)로 보냈다.

| 10문항 | 벽시계 중앙값 | 평균 | 최소~최대 | 첫 검색 중앙값 |
|---|---:|---:|---:|---:|
| CLI | 67.2초 | 68.4초 | 64.8~76.2초 | 65.3초 |
| **서버** | **6.0초** | **6.6초** | 4.1~12.7초 | 6.0초 |

**이 비교에는 모델 호출 시간이 빠져 있다.** 이 10문항은 9장에서 DeepSeek로 같은 입력을 돌린 적이 있어, 두 쪽 모두 저장된 모델 응답을 다시 썼다. 그래서 벽시계는 거의 준비 + 검색 시간이다. CLI와 서버의 차이(약 61초)는 질문마다 모델을 다시 불러오는 비용이다.

### 새 질문(모델을 실제로 부름)

| 질문 | 서버 벽시계 | 검색 횟수 |
|---|---:|---:|
| 전자금융업자가 이용자 자금을 보호하기 위해 해야 하는 조치는? | 15.6초 | 2 |
| 신용정보회사 임원의 결격사유는 무엇인가요? | 16.5초 | 1 |
| 금융상품판매업자가 적합성 원칙을 어기면 어떤 제재를 받나요? (스트리밍) | 33.8초 | 3 |

CLI로 같은 질문을 하면 여기에 약 61초가 더 붙는다(위 표의 차이). 비용은 셋 합쳐 약 0.005달러였다.

스트리밍 응답(`/ask/stream`)은 이렇게 왔다(앞 숫자는 요청부터 걸린 초).

```text
  0.0s start
 13.3s tool   search → 금융소비자보호법 제52조, 제17조, 제51조 …
 16.9s llm    입력 4,329토큰, 출력 205토큰, 3.6초
 16.9s tool   get_article 금융소비자보호법 제51조
 16.9s tool   get_article 금융소비자보호법 제52조
 22.4s tool   search "적합성원칙 위반 시정명령 과징금"
 25.0s llm    입력 9,876토큰 …
 29.1s tool   search, get_article 제50조
 33.8s llm    입력 12,911토큰, 출력 686토큰
 33.8s answer
```

사용자는 13초 만에 "어떤 조문을 찾았는지"를 보고, 34초에 답을 받는다.

## 한계

- CLI와 서버 비교는 10문항이고, 모델 응답이 저장된 문항이라 모델 호출 시간이 빠져 있다. 준비 시간의 차이만 잰 것이다.
- **저장된 모델 응답을 다시 쓰면 기록의 모델 호출 시간은 처음 호출했을 때의 값이다**(9장부터 그렇다). 그래서 이 10문항의 기록에서는 "모델 호출 합"이 벽시계보다 길게 나온다. 기록에 "저장된 응답" 표시를 넣지 않았다.
- 질문을 하나씩 처리하므로 동시에 여러 사람이 물으면 줄을 선다. 동시 처리는 검색 모델을 여러 벌 올리거나 GPU 작업만 줄 세우는 식으로 해야 하고, 재지 않았다.
- 스트리밍은 단계 단위다. 답 글자를 토큰 단위로 흘리려면 대화 클라이언트를 스트리밍 모드로 바꿔야 한다.
- 인증이 없다. 계획서대로 로컬(127.0.0.1)에서만 연다. 공개 배포는 하지 않는다.
- 모델을 띄워 두는 동안 검색·재정렬 모델이 메모리를 계속 차지한다. 얼마나 쓰는지는 재지 않았다.

## 다시 돌리기

```bash
pip install -e '.[serve]'
proviso serve --port 8000          # 준비에 약 1분
curl -s localhost:8000/health
curl -s -X POST localhost:8000/ask -H 'content-type: application/json' -d '{"question": "신용정보회사 임원의 결격사유는 무엇인가요?"}'
curl -N "localhost:8000/ask/stream?q=적합성%20원칙을%20어기면"
```

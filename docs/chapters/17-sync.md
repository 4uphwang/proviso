# 17장. 법령이 바뀌면 처음부터 다시 만든다: 증분 동기화

## 문제

법령은 11월 20일에 한 번 통째로 받았다. 그 뒤에 개정이 생기면 proviso는 모른다. 다시 맞추려면 `proviso collect --all`(본문은 이미 받은 것을 건너뛴다) → `proviso load`(484개 버전을 모두 다시 파싱·적재) → `proviso index build`(bge-m3로 현행 색인 232초 + 모든 본문 기간 색인 1,123초)를 다 해야 했다. 개정 몇 건 때문에 조각 1만 3천여 개를 다시 임베딩한다. 계획서 §4.4의 증분 동기화를 이 장에서 넣는다.

## 처방: `proviso sync`

1. 법령마다 시행일 버전 목록을 새로 받아 DB와 비교한다. 새 버전, 상태가 바뀐 버전(시행예정 → 현행 등), 목록에서 사라진 버전을 가른다.
2. 아직 없는 본문만 받는다.
3. **새 버전만** 파싱해 넣고, 그 문서의 기간(`valid_to`)을 다시 계산하고, 위임 연결을 다시 잇고, 새 스냅샷을 만든다(한 트랜잭션). 사라진 버전은 지우지 않고 보고서에만 남긴다. 과거 시점 질문(7장)에 답해야 하기 때문이다.
4. 색인마다 새 색인을 만들되, **글이 같은 조각은 이전 색인의 임베딩을 그대로 쓰고** 바뀐 조각만 임베딩한다(`build_index(reuse=…)`). 새 색인은 점검(그날의 모든 현행 조문이 조각에 있는가)을 통과해야 쓰인다. 못 통과하면 새 색인을 지우고 이전 색인을 그대로 쓴다(blue-green).
5. 보고서 `runs/sync/<날짜>.md`: 추가·변경·삭제된 현행 조문, 새로 생긴 시행 예정 버전, 색인별 새로 임베딩한 조각 수, **정답 조문의 현행 본문이 바뀐 평가 문항**(다시 확인할 대상). 시점 문항은 시행일로 정답이 고정돼 있어 영향이 없다.

바뀐 것이 없으면 아무것도 쓰지 않고 "변경 없음"만 보고한다. 같은 목록으로 다시 돌려도 결과가 같다(테스트로 확인).

## 실제로 돌린 결과

11월 24일에 실제 DB에 돌렸다. 8개 법령 484개 버전 모두 DB와 같았고, 새 버전·상태 변경·사라진 버전이 없었다. 목록을 받고 비교하는 데 3초 걸렸고 보고서는 "변경 없음"이었다(`runs/sync/20261124.md`). 그래서 실제 개정으로는 동작을 확인할 수 없었다.

## 되돌려서 확인한 것

실제 DB를 `proviso_sync`로 복사하고, **2025년 7월 1일 뒤에 공포된 버전 42개를 뺐다.** 그때 수집했다면 이런 상태였을 것이다. 되돌린 상태의 색인(현행, 모든 본문 기간)도 만들어 두고, 원래 색인은 지웠다. 그다음 지금의 버전 목록으로 `sync`를 돌렸다. 원본 본문은 이미 받아 둔 것이라 받는 단계는 빠진다.

| sync가 한 일 | |
|---|---:|
| 넣은 새 버전 | 42 |
| 현행 조문(2026-11-20 기준) 추가 / 변경 / 삭제 | 21 / 101 / 0 |
| 새로 생긴 시행 예정 버전 | 3 (자본시장법 2026-12-09, 2027-02-04, 전자금융거래법 2026-12-17) |
| 현행 색인: 조각 / 새로 임베딩 | 2,530 / **280** |
| 모든 본문 기간 색인: 조각 / 새로 임베딩 | 11,059 / **352** |
| 정답 조문이 바뀐 평가 문항 | 128 (검색 세트 94, 에이전트 세트 34) |

| 걸린 시간 | sync | 전부 다시 만들 때 |
|---|---:|---:|
| 적재 | 15.1초 | (484개 버전 전부) |
| 현행 색인 | 37.9초 | 231.6초 |
| 모든 본문 기간 색인 | 60.4초 | 1,122.6초 |
| 합 | **113.4초** | 약 23분 + 적재 |

**결과를 실제 DB와 비교했다.** sync가 만든 DB가 처음부터 다 넣은 실제 DB와 같아야 한다.

| | 실제 DB | sync 결과 | 다른 것 |
|---|---:|---:|---:|
| 법령 버전 | 484 | 484 | 0 |
| 조문 기간(span) | 146,575 | 146,575 | 0 |
| 위임 연결 | 2,047 | 2,047 | 0 |
| 현행 색인 조각(글·조문·임베딩) | 2,530 | 2,530 | 0 |
| 모든 본문 기간 색인 조각 | 11,059 | 11,059 | 0 |

색인 조각은 글과 가리키는 조문뿐 아니라 임베딩 값까지 모두 같았다. 새로 임베딩한 조각도 같은 모델이라 실제 DB 값과 같았다.

### 비교하다 찾은 것: 스냅샷 해시가 찌꺼기에 흔들렸다

본문(`article_texts`)은 실제 DB가 331개 더 많았고, 그래서 스냅샷의 내용 해시가 달랐다. 그 331개는 **어떤 기간도 가리키지 않는 본문**이었다. 같은 시행일 버전 두 개를 차례로 넣을 때 앞 것이 덮어써지며 남는 것이다. 되돌리는 스크립트가 이런 본문을 지워서 차이가 났다. sync 탓이 아니다.

가리키는 본문만 세면 두 DB 모두 4,648개이고 해시가 같았다. 스냅샷은 "내용이 같으면 같은 값"이어야 하므로, `create_snapshot`이 가리키는 본문만 해시하도록 고쳤다. 기존 스냅샷 id는 그대로이고, 다음 적재부터 적용된다.

### 평가셋 영향 128문항

되돌린 실험에서 sync는 128문항을 "정답 조문의 현행 본문이 바뀜"으로 표시했다. 이 평가셋은 11월 20일 본문으로 만들었으니, 7월 상태에서 출발한 이 실험에서 표시되는 것이 맞다. 실제 sync에서는 0개였다. 표시는 보고서에만 하고 평가셋 파일은 고치지 않는다. 사람이 확인해야 한다.

## 한계

- 실제 개정으로는 확인하지 못했다(11월 20일 이후 개정 없음). 되돌린 실험은 "새 버전이 늘어난" 경우만 본다. 되돌린 DB의 버전 상태(현행·연혁)는 11월 20일 값 그대로여서 상태 변경은 0개였다. 상태 변경은 단위 테스트로만 확인했다.
- 목록에서 사라진 버전(법령 폐지, 잘못 올라온 버전 삭제)은 보고만 하고 처리하지 않는다. 지금 데이터에는 없다.
- 색인 점검은 "현행 조문이 모두 들어 있는가"뿐이다. 계획서의 "검색 test로 회귀 확인"은 임베딩 모델·청킹이 바뀔 때의 절차이고(12장에서 손으로 했다), sync에 넣지 않았다.
- 새 색인의 기준일은 sync를 돌린 날이다. 평가 실행은 기준일을 2026-11-20으로 고정해 두었으므로, 새 개정이 생기면 평가 숫자와 비교할 때 기준일을 맞춰야 한다.
- 법령 API는 등록한 IP에서만 된다. 정기 실행(launchd)은 넣지 않았다.
- 답변 캐시 무효화는 답변 캐시가 없어(선택 6번) 하지 않았다. 모델 응답 저장(9장)은 입력이 바뀌면 다른 키가 되므로 따로 지울 필요가 없다.

## 다시 돌리기

```bash
proviso sync                    # 목록 받기 → 새 버전만 적재 → 바뀐 조각만 임베딩 → runs/sync/<날짜>.md
proviso sync --no-index         # 적재만
pytest tests/test_sync.py       # 법률 제1조만 바뀐 새 버전: 조각 1개만 임베딩, 다시 돌리면 변경 없음
```

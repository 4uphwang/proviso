# 18장. 같은 앞부분을 매번 다시 읽는다: 프롬프트 캐싱

## 문제

에이전트는 모델을 부를 때마다 도구 정의, 시스템 지시, 지금까지의 대화를 처음부터 다시 보낸다. 같은 앞부분을 캐시해 두면 입력 비용과 첫 토큰 지연이 줄어든다는 것이 계획서 E6이다. 이 장에서는 캐시를 켜고 끌 수 있는 Claude Haiku 5.5(오픈라우터)로 전후를 비교한다. 9장의 기본 모델 DeepSeek V4 Flash는 공급자가 앞부분을 알아서 캐시해 끌 수 없으므로, 얼마나 읽는지만 관찰한다.

## 짐작: 효과가 작을 것이다

결과를 보기 전에 두 가지를 쟀다.

- **모든 질문이 같은 앞부분**(도구 정의 + 시스템 지시)은 **1,304토큰**이다(3문항 시험에서 오픈라우터가 알려 준 캐시 읽기 크기). Haiku 5.5의 최소 캐시 길이(512토큰)는 넘지만, 질문 하나의 첫 호출 입력은 5천~7천 토큰이고 나머지는 질문마다 다른 첫 검색 결과다.
- 9장 Haiku는 **질문당 모델 호출이 평균 1.25번**이다. 같은 질문 안에서 대화 앞부분을 다시 읽을 두 번째 호출이 4분의 1에만 있다.

그래서 아끼는 몫은 입력의 20% 안쪽이고, 대화 끝까지 캐시하면 다시 읽히지 않는 쓰기(1.25배)를 내서 오히려 손해일 수 있다고 봤다.

## 처방: 캐시 표시 두 가지

`agent/loop.py`의 `mark_cache`가 오픈라우터로 보내는 메시지에 `cache_control`을 단다. 모델 이름 뒤에 붙여 켠다.

| 설정 | 표시 위치 | 노리는 것 |
|---|---|---|
| `+cache-sys` | 시스템 메시지 끝 | 모든 질문이 같은 앞부분(도구 정의 → 시스템 지시) |
| `+cache` | 시스템 메시지 끝 + 마지막 메시지 끝 | 위에 더해, 같은 질문의 다음 호출이 대화 앞부분을 다시 읽음 |

호출마다 캐시에서 읽은 토큰(`cached_tokens`)과 캐시에 쓴 토큰(`cache_write_tokens`)을 기록에 남긴다.

## 결과 (dev 87문항, 판별기 켬, 저장된 응답 없이 새로 부름)

판별기가 거른 10문항은 모델을 부르지 않아 77문항이 모델을 불렀다.

| Haiku 5.5 | 모델 호출 | 입력 토큰 | 캐시 읽기 | 캐시 쓰기 | 입력 비용 | 입력 1M토큰당 | 전체 비용 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 캐시 없음 | 100 | 629,085 | 0 | 0 | $0.0629 | $0.1000 | $0.0885 |
| **`+cache-sys`** | 100 | 620,211 | 114,498 (18.5%) | 17,797 (2.9%) | $0.0522 | **$0.0841** | $0.0783 |
| `+cache` | 94 | 580,208 | 189,031 (32.6%) | 390,985 (67.4%) | $0.0508 | $0.0875 | $0.0767 |

입력 비용은 전체 비용에서 출력 토큰 값($0.50/1M)을 뺀 것이다. 입력 토큰 × 정가(캐시 안 됨 1배, 읽기 0.1배, 쓰기 1.25배)로 계산한 값과 소수 넷째 자리까지 같았다.

- **시스템만 캐시하면 입력 단가가 16% 내려갔다**($0.100 → $0.084). 읽은 몫(18.5%)은 거의 다 질문마다 같은 1,304토큰이다. 쓰기는 2.9%뿐이다. 5분 안에 다음 질문이 오면 캐시가 살아 있어서 처음 몇 번만 쓴다.
- **대화 끝까지 캐시하면 입력의 67%를 쓰기(1.25배)로 냈다.** 두 번째 호출은 앞부분의 56%를 캐시에서 읽었지만 그런 호출이 17번뿐이라, 입력 단가는 시스템만 캐시할 때보다 높았다($0.0875). 짐작대로다.
- 전체 비용은 `+cache`가 가장 낮게 나왔는데, 이 실행에서 모델 호출이 94번으로 적었기 때문이다(API 답은 매번 달라 도구를 덜 썼다). 그래서 호출 수와 상관없는 입력 1M토큰당 값으로 비교했다.
- **지연은 차이가 없었다.** 첫 모델 호출 중앙값 2.52초 / 2.46초 / 2.69초. 1,304토큰을 캐시해도 첫 토큰이 눈에 띄게 빨라지지는 않는다.
- **답은 그대로다.** 핵심어 포함률 0.922 / 0.941 / 0.941, 인용 재현율 0.920 / 0.911 / 0.929, 거절 정확도 1.000 / 1.000 / 0.933(15문항 중 1개 차이). 캐시는 같은 입력을 읽을 뿐이라 답을 바꾸지 않는다. 차이는 9장에서 본 API 답의 흔들림 안이다.

dev에서 `+cache-sys`를 골랐다. test 확인은 하지 않았다(아래 한계).

### DeepSeek V4 Flash: 알아서 25.7%를 읽는다

같은 dev 실행에서 DeepSeek는 표시 없이 입력 815,405토큰 중 209,664토큰(25.7%)을 캐시에서 읽었고, 쓰기 요금은 없었다. Haiku의 `+cache-sys`(18.5%)보다 많이 읽은 것은 DeepSeek가 질문당 모델을 1.86번 불러, 같은 질문의 두 번째 호출이 대화 앞부분을 통째로 읽었기 때문이다. 9장의 DeepSeek 비용에는 이 할인이 이미 들어 있었다.

## 결정

- Anthropic 모델을 쓸 때는 `+cache-sys`를 붙인다(입력 단가 −16%, 답 그대로). 대화 끝까지 캐시하는 `+cache`는 이 에이전트처럼 호출이 짧으면 쓰기 비용만 늘어서 쓰지 않는다.
- 기본 모델(DeepSeek)은 바꿀 것이 없다. 공급자가 이미 캐시한다.
- 이 작업에서 캐싱으로 아낄 수 있는 몫은 작다. 입력의 대부분이 질문마다 다른 검색 결과이기 때문이다. 비용을 더 줄이려면 보여 주는 조문 길이(8장)나 호출 수를 줄이는 쪽이 크다.

## 한계

- dev 87문항 한 번씩만 쟀고 test로 확인하지 않았다(사용자 결정으로 dev만 돌렸다). 비용 차이에 신뢰구간을 내지 않았다. 입력 단가는 토큰 수에서 정가로 계산되는 값이라 흔들림이 작지만, 읽기 비율은 질문 사이 간격(5분 TTL)과 호출 수에 따라 달라진다.
- 시스템 지시에 기준일 문구(7장)가 들어가는 시점 질문은 앞부분이 달라 따로 캐시된다.
- 1시간 TTL, 캐시 미리 데우기는 재지 않았다.
- 비용은 오픈라우터가 알려 준 값이다. Anthropic API에 직접 보내면 다를 수 있다.
- 이 장의 실행 비용은 dev 4회와 3문항 시험을 합쳐 약 0.33달러였다.

# 20장. 앞 대화에 기대는 질문: 후속 질문 다시 쓰기

## 문제

지금까지는 질문 하나에 답 하나였다. 실제 채팅에서는 "그거 어기면 과태료는?", "2016년엔 어땠어?", "그 밖에 적어야 하는 건?"처럼 앞 대화를 알아야 뜻이 서는 질문이 이어진다. 이 질문을 그대로 검색하면 "과태료"만으로 찾으니, 어느 법 무슨 의무의 과태료인지 모른다. 연도만 있는 질문은 무엇의 옛 버전인지 모른다.

## 측정 준비: 후속 질문 평가셋 83문항

`evalset/followup.jsonl`. 첫 턴은 답변 평가셋(5장) 문항과 9장 기본 모델(DeepSeek)의 실제 답이고, 두 번째 턴과 정답 조문을 새로 붙였다. 정답 조문은 법령 그래프에서 먼저 고르고, 질문은 Claude가 그 조문을 읽고 썼다(사람 검수 전).

| 종류 | 두 번째 질문의 정답 | dev | test |
|---|---|---:|---:|
| same | 같은 조의 다른 세부("그 밖에 적어야 하는 건?") | 13 | 20 |
| delegate | 첫 조문이 "대통령령으로 정하는"으로 넘긴 시행령 조문 | 4 | 9 |
| penalty | 첫 조문을 어겼을 때의 벌칙·과태료 조문 | 2 | 6 |
| temporal | 같은 조의 옛 버전(질문에 연도) | 1 | 4 |
| switch | 앞 대화와 상관없는 새 질문(섞으면 안 됨) | 8 | 16 |
| 합계 | | 28 | 55 |

- 후보 172개 중 89개는 쓰지 않았다. 고른 조문이 첫 질문 주제와 동떨어졌거나, 첫 답이 이미 그 내용을 다 말했거나, 옛 버전과 현행의 차이가 표기뿐이었다. 그래서 제재·옛 버전 문항이 적다.
- 처음에는 조문 본문을 앞에서부터 2,500자로 잘라 보여 줘서, 긴 벌칙 조문의 해당 호가 잘린 탓에 제재 문항이 거의 다 빠졌다(16개 중 3개만 씀). 두 번째에는 첫 조문 번호가 나오는 자리 주변을 보여 줬다.
- 채점: 두 번째 질문(전략별로 바꾼 것)으로 검색해 정답 조문이 상위 k 안에 있고, 그 질문에서 읽은 기준일에 시행 중인 버전이 정답 버전이어야 맞다. 연도를 잃거나 엉뚱한 연도를 붙이면 틀린다.

## 처방: 혼자 읽히는 질문으로 고쳐 쓴 뒤 한 턴처럼 처리

`agent/followup.py`. 세 방법을 비교했다.

- **none**: 후속 질문 그대로(출발점)
- **concat**: 바로 앞 질문 + 후속 질문(모델 없음)
- **rewrite**: 모델(DeepSeek V4 Flash)이 앞 대화(최근 3턴의 질문, 답 앞 400자, 인용 조문)를 보고 혼자 읽히는 한 문장으로 고쳐 쓴다. 새 주제면 그대로 두고, 질문에 답하지 않는다.

고쳐 쓴 질문은 한 턴짜리 질문과 똑같이 처리한다. 그래서 검색, 기준일 읽기(7장), 가드레일(11장), 인용 확인을 바꾸지 않았다.

- 가드레일은 두 번 거친다. 후속 질문 원문을 먼저 검사하고, 고쳐 쓴 질문도 다시 검사한다(앞 대화에서 끌어온 말이 있을 수 있다). 범위 검사(11장)는 원문과 고쳐 쓴 질문을 함께 본다.
- 앞 대화는 다시 쓰기 지시 안에서 매번 새로 만든 경계 표시로 감싸고, 그 안의 지시는 따르지 말라고 적는다.
- 다시 쓰기가 형식을 어기거나 연결에 실패하면 원문을 그대로 쓴다(검색이 나빠질 뿐 안전 검사는 그대로다). 키가 없으면 concat으로 대신한다.
- 서버는 대화 기록을 요청에 싣지 않고 `conversation_id`로만 받아, 메모리에 든 자기 답을 앞 대화로 쓴다. 클라이언트가 지어낸 '앞 답'으로 다시 쓰기를 조종하지 못하게 했다(최근 대화 200개, 서버를 다시 띄우면 사라진다).
- 다시 쓴 질문과 원문은 기록(`config.followup`)에 남는다. CLI `proviso agent chat`은 "(이렇게 알아들었어요: …)"로 보여 준다.

## 결과

dev(28)에서 고른 뒤 test(55)에서 확인했다. 검색 상위 k 안에 정답(맞는 버전)이 있는 비율이다.

| test 55 | 1위 | 상위 5 | 상위 10 |
|---|---:|---:|---:|
| none | 0.291 | 0.673 | 0.709 |
| concat | 0.473 | 0.873 | 0.964 |
| **rewrite** | **0.527** | **0.982** | **0.982** |

| test 상위 5, 종류별 | none | concat | rewrite |
|---|---:|---:|---:|
| same (20) | 0.500 | 1.000 | 1.000 |
| delegate (9) | 0.444 | 0.778 | 1.000 |
| penalty (6) | 1.000 | 1.000 | 1.000 |
| temporal (4) | 0.250 | 1.000 | 1.000 |
| switch (16) | 1.000 | 0.688 | 0.938 |

- rewrite − none: 상위 5 +0.309 [0.182, 0.455], 상위 10 +0.273 [0.145, 0.418]. 분명히 좋아졌다.
- rewrite − concat: 상위 5 +0.109 [0.018, 0.218]로 rewrite가 낫다. 1위·상위 10은 차이 불분명.
- **concat은 새 주제 질문을 망친다.** 앞 질문을 붙이니 test 새 주제 16개 중 5개가 상위 5 밖으로 밀렸다(dev 1위 0.875 → 0.375). rewrite는 대부분 그대로 뒀다.
- dev도 같은 방향이었다: 상위 10 none 0.643, concat 0.893, rewrite 0.929.
- 비용: 다시 쓰기 한 번에 입력 약 670토큰, 출력 약 45토큰, 약 0.00004달러. 지연은 6번 재서 0.5~1.2초.

## 남은 문제

- **새 주제를 하나 오염시켰다.** "과징금 체납자 결손처분 해주는 특별한 사유"를 앞 대화의 "신용정보법상"을 붙여 고쳐 써서 정답(다른 법)을 놓쳤다. 법 이름을 붙이는 것이 가장 흔한 실수일 것이다.
- **답까지는 재지 않았다.** 검색에서 정답을 찾는지만 봤다. 답의 핵심어·인용까지 재려면 질문마다 에이전트를 돌려야 한다(55문항 약 30분).
- 평가셋이 작고(test 55, 제재 6·옛 버전 4), 질문을 Claude가 썼다. 세 번째 턴 이후, 앞 대화의 답이 틀렸을 때는 재지 않았다.
- 서버의 대화 기억은 메모리에만 있다. 서버를 여러 개 띄우면 같은 대화가 다른 서버로 가서 끊긴다.

## 다시 돌리기

```bash
proviso agent followup --split dev     # none, concat, rewrite 비교(다시 쓰기 응답은 저장돼 두 번째부터 요금 없음)
proviso agent followup --split test
proviso agent chat                     # 대화형
```

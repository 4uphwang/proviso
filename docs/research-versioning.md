# 법령 연혁 전체 수집 분량 조사 (2026-11-20)

## 1. 법령 API가 주는 것
국가법령정보센터 Open API 활용가이드 기준.

| API | 요청 | 형식 | 쓰임 |
|---|---|---|---|
| 법령 연혁 목록 | `lawSearch.do?target=lsHistory&query=…` | **HTML만** | 버전 목록(공포일, 시행일, 제개정 구분, MST) |
| 법령 연혁 본문 | `lawService.do?target=lsHistory&MST=…` | **HTML만** | 특정 버전 본문 |
| 법령 본문 | `lawService.do?target=law&MST=…` | JSON/XML | MST(버전 고유번호)로 본문. 과거 MST도 되는지는 키 받은 뒤 확인 |
| 조문별 변경 이력 | `lawService.do?target=lsJoHstInf&ID=…&JO=000200` | JSON/XML | 한 조가 언제 바뀌었는지(조문변경일, 변경사유) |
| 일자별 조문 개정 이력 | (가이드 `lsDayJoRvsListGuide`) | 확인 필요 | 날짜별로 바뀐 조문 |

정리: 연혁 **목록**은 HTML을 파싱해야 한다. 과거 버전 **본문**은 `target=law&MST=<과거 MST>`가 JSON으로 되면 현행과 같은 파서를 쓴다. 안 되면 연혁 본문 HTML 파서가 하나 더 필요하다(+0.5일).

## 2. 법령 4개의 분량
국가법령정보센터 웹사이트의 연혁 목록과 현행 본문 기준이다(한국어 버전만, 2026-11-20 확인).

| 법령 | 버전 수 | 최초 | 2016년 이후 | 2021년 이후 | 현행 조문 수 | 현행 본문 글자 수 |
|---|---:|---|---:|---:|---:|---:|
| 자본시장법 | 91 | 2009 시행(2007 제정) | 61 | 33 | 565 | 약 53만 |
| 신용정보법 | 48 | 1995 | 19 | 8 | 92 | 약 10만 |
| 전자금융거래법 | 24 | 2007 | 12 | 4 | 71 | 약 7만 |
| 금융소비자보호법 | 8 | 2021 | 8 | 8 | 76 | 약 6만 |
| **합계** | **171** | | **100** | **53** | **약 800** | **약 76만** |

- 제개정 구분: 자본시장법은 일부개정 51, 타법개정 39. 신용정보법은 2009년쯤 전부개정이 1번 있어서 그 전후로 조 번호 체계가 다르다.
- **시행 예정 버전이 이미 있다**: 전자금융거래법은 2026-12-17 시행, 자본시장법은 2027-02-04 시행 버전이 공포돼 있다. 연혁을 다루지 않아도 "현행"과 "시행 예정"은 구분해야 한다.

## 3. 저장·색인 분량 추정
- 버전마다 조문을 다 저장하면 약 5.8만 행이다(자본시장법 91 × 565가 대부분).
- 대부분의 조문은 개정 사이에 바뀌지 않는다. 본문 해시로 중복을 없애면 **고유 조문은 3천~5천 개 정도**로 예상한다(현행 800개 + 개정마다 바뀐 조문). 정확한 값은 수집한 뒤 센다.
- 원본 수집: API 호출 약 200회, 원본 약 50~100MB. 상태 저장·재개가 있어서 문제없다.
- 임베딩: 고유 조문만 임베딩하면 로컬 bge-m3로 수십 분 이내다. Gemini 임베딩 API로도 비용은 매우 작다.
- 결론: **데이터 양은 문제가 아니다.** 어려운 건 아래 정확성 문제다.

## 4. 진짜 어려운 부분
1. **부칙의 부분 시행**: "다만, 제X조의 개정규정은 공포 후 1년이 지난 날부터 시행한다" 같은 조항 때문에 같은 버전 안에서도 조마다 시행일이 다르다. 버전 시행일만 쓰면 일부 조문의 유효 기간이 틀린다.
   - 대응 A: 버전 시행일만 쓰고 한계로 명시
   - 대응 B: `조문별 변경 이력` API의 조문변경일로 조별 유효 기간 보정(+1일)
2. **조 번호가 바뀜**: 전부개정, 조문 이동, 삭제("삭제 <2020. 6. 9.>") 때문에 같은 번호가 다른 내용일 수 있다. 조의 "정체성"은 추적하지 않고 (법령, 조 번호, 유효 기간)으로만 다룬다.
3. **검색 중복**: 같은 본문이 여러 버전에 걸쳐 있어 검색 결과가 같은 조문으로 도배될 수 있다. 고유 본문 단위로 색인하고 버전별 유효 기간은 매핑 테이블로 둔다. 질의 시 `as_of`로 거른다.
4. **평가셋**: 시점 질문의 정답을 과거 원문으로 직접 확인해야 해서 문항당 시간이 더 든다.
5. **오래된 원문 형식**: 1990~2000년대 법령은 표기가 달라 파서 예외가 생길 수 있다(신용정보법 1995).

## 5. 일정 영향(연혁 전체 = 3번)
| 작업 | 추가 기간 |
|---|---|
| 연혁 목록 HTML 파싱 + 과거 버전 본문 수집(JSON 되면 파서 재사용) | 0.5~1일 |
| 버전 모델(고유 본문 + 버전·유효 기간 매핑), 변경 감지, 바뀐 것만 재임베딩 | 1일 |
| `as_of` 검색·도구, 시행일을 붙인 인용, 시행 예정 구분 | 0.5일 |
| 시점 평가 문항 8~10개(과거 원문으로 정답 확인) + 지표 | 1일 |
| (선택) 부칙 부분 시행을 조별 유효 기간으로 보정 | 1일 |
| **합계** | **약 3~4일 (보정 포함 4~5일)** |

필수 범위가 10~12일에서 **13~16일**로 늘어난다.
